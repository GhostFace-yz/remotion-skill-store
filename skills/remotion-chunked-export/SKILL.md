# 长片稳定导出：分块渲染 + 整段音频

## 症状与判断

出现下面任一情况，就用这套流程：

- 导出的成片**间歇性黑帧/闪烁**（尤其画面里有 `<Video>`、`<OffthreadVideo>`、`@remotion/media` 视频贴图）
- 片长超过 ~1500 帧，一开始正常，后面开始丢帧
- 用 `--concurrency` 调高之后反而更糟

先做一个 30 秒能做完的判断实验，别急着改代码：

1. 把视频贴图用的 canvas 初始填充色临时改成品红（`#ff00ff`），渲染同一段
2. 如果"黑帧"位置变成了品红 → **不是**材质、光照、网格的问题，是**贴图根本没收到视频帧**
3. 如果还是黑 → 才去看材质/相机/光照

这一步在真实项目里省掉了一整天的排查。

## 根因

Remotion 每个渲染标签页各自解码视频。素材越大（本项目 143 MB / 3491 帧），并发标签页越多，越容易出现"某个标签页再也拿不到帧"，于是该标签页负责的帧就画成空画面。

实测（600 帧区间，同一素材同一参数）：

| 并发 | 黑帧 |
|---|---|
| 默认（十几路） | 40 帧（6.6%） |
| 4 | 91 帧（15%） |
| 2 | 0 帧 |

但**整片 2897 帧用 2 路渲染仍然会崩**（1182 帧黑）——标签页跑太久就会退化。所以不能只降并发，必须**分块**：短生命周期的标签页，每次只跑 600 帧。

## 算法

```
for 每 600 帧:
    render --codec=h264 --muted --concurrency=2 --frames=a-b  → chunk-N.mp4
ffmpeg -f concat -c copy                                      → video.mp4
render --codec=wav --muted=false --frames=0-end                → audio.wav   # 整段，一次
ffmpeg -i video.mp4 -i audio.wav -c:v copy -c:a aac -b:a 320k -shortest  → final.mp4
ffprobe 校验帧数
```

三个关键决定：

1. **视频分块 + `-c copy` 拼接**：同一编码参数下 concat demuxer 可以无损拼接，不重编码。
2. **音频整段单独渲染**：音频渲染不涉及画面，不受解码退化影响；而且避免"每块 AAC 都有 priming samples"，拼起来会有一串几毫秒的缝隙/咔哒声。
3. **最后 mux**：`-c:v copy` 保证视频不再被压一次。

## 参数怎么调

| 参数 | 建议 | 说明 |
|---|---|---|
| `CHUNK_FRAMES` | 600 | 有视频素材时 600 内实测稳定；纯 3D/2D 可以放到 1200 |
| `CONCURRENCY` | 2 | 有视频素材用 2；纯帧驱动画面可以 4–8 |
| `--image-format=png` | 有 | 避免 jpeg 中间帧的色块，代价是慢一点 |
| `--muted` | 分块时必开 | 音频单独出，别让每块都解码音频 |

## 验收（不跑这个不算完成）

`bash assets/verify-export.mjs out/final.mp4`（也可以 `--crop=x,y,w,h` 只看屏幕区域）会输出：

- 黑帧数量与位置（平均值低于阈值即判黑）
- 帧间亮度差的中位数 / p99 / 最大值（判断闪烁）
- 音频每米秒的 RMS 与异常静音段（判断拼接点断音）

本项目基线：**0 黑帧、帧间亮度差中位 0.22**（修复前是 1182 黑帧、12.77）。

## 常见坑

1. **`--shortest` 必须加**：音频比视频长（或反之）时，不加会出尾部黑屏。
2. **拼接块必须同参数**：分辨率、fps、pix_fmt、编码器全都一致，否则 `-c copy` 拼出来的文件在某些播放器上卡死。
3. **别用 `-crf` 不同的块**：分块渲染时不要中途改参数。
4. **`-movflags +faststart`** 放在最后一步 mux 上加（网页/平台上传更友好）。
5. **帧数校验**：mux 完用 `ffprobe` 比对 `nb_frames` 与预期，少了就说明某块渲染失败被静默跳过。
6. **临时目录别复用**：每次 `rm -rf` 分块目录，残留旧块会导致拼接顺序错乱。
